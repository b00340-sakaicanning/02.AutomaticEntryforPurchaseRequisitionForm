# 04 業務ロジック仕様

- 版: v1.1（2026/10/31。デザインとコピペ反映の方針を追加）
- 主な実装先: 【Workflow】、【Validator】、【Auth】、【MaterialMatcher】、【CsvExport】、【Attachment】、【MasterImport】、【Repository】

## 3. 権限

### 3.1 役割の判定（【Auth】 の `resolveRoles(operatorId, request)`）

| 役割 | 判定 | 暗証番号 |
|------|------|----------|
| 入力者 | `request.applicantId === operatorId`。新規作成のときは、操作者が入力者になる | 不要 |
| 指定承認者 | `request.approverId === operatorId` かつ `request.applicantId !== operatorId`（D-17、K-01） | 必要 |
| 管理者 | 権限マスタに `役割=管理者`・`有効=TRUE` の行がある | 必要 |
| 経理 | 権限マスタに `役割=経理`・`有効=TRUE` の行がある | 必要 |

- 操作者は、社員マスタで `有効=TRUE` でなければならない。無効ならエラーコード `FORBIDDEN` を返す。

**画面に出すときの扱い**
- 一覧・詳細・添付の閲覧は、全員ができる（K-26、K-41）。
- 【Workflow】 に、この表を `PERMISSIONS` 定数（action × ステータス → 許可する役割の配列）として持つ。
- 判定する関数は `canPerform(action, request, roles)` にする。
- 画面のボタンの活性判定にも同じ表を使えるように、`getInitData()` でクライアントへ渡す。

**修正の制限（K-05、K-06）**
- 承認依頼中・承認済の届出を修正するときは、部門・承認者を変更できない。サーバー側でも、変更されていたらエラー `VALIDATION` を返す。
- 入力者は、どのステータスでも変えない。

### 3.3 暗証番号が必要かどうか
1. その操作を許可された役割の中に「入力者」があり、操作者がその届出の入力者なら、**暗証番号は不要**。
2. 上に当たらず、許可された役割（承認者・管理者・経理）に操作者が当たる場合は、**有効なトークンが必要**。
   - トークンが無い、または期限切れなら、エラー `AUTH_REQUIRED` を返す。画面は暗証番号の入力ダイアログを出し、認証できたら同じ操作をやり直す。
3. どの役割にも当たらなければ、エラー `FORBIDDEN` を返す。

### 3.4 暗証番号の発行と認証（K-13、K-37、U-07）
- **管理者による番号の指定**（2026/11/01 追加。K-13）
  - マスタ管理タブ・メニュー「暗証番号を発行」で、ランダムの代わりに番号を指定して設定できる。
  - 形式チェック `validatePin_(pin, PIN_LENGTH)`: 数字だけ、桁数は `PIN_LENGTH` と同じ。全角数字は半角に直す。推測しやすい番号（123456 など）も許可する。
  - 指定したときは番号を戻り値で返さない。操作ログには「指定／ランダム」だけを残し、番号は残さない。
  - 管理者が自分の暗証番号を変えたときは、画面がその場で認証を解除する（次の操作で新しい番号を求める）。
- **発行**（`issuePin(employeeId)`。管理者だけ）
  1. 数字 `PIN_LENGTH` 桁を乱数で作る（`Math.random` ではなく、`Utilities.getUuid()` から数字を取り出すなど、偏りの少ない方法を使う）。
  2. 新しいソルトを作り、`hash = hex(SHA-256(salt + ":" + pin))` を求める（`Utilities.computeDigest(Utilities.DigestAlgorithm.SHA_256, str, Utilities.Charset.UTF_8)`）。
  3. 暗証番号シートに書く（既存の行は上書き。失敗回数は0、ロックは解除）。
  4. 平文の暗証番号は、戻り値で**1回だけ**返す。どこにも保存しない。
- **認証**（`authenticate(operatorId, pin)`）
  1. ロック解除日時が今より後なら、エラー `AUTH_LOCKED` を返す（解除される時刻をメッセージに入れる）。
  2. ハッシュが一致しなければ、失敗回数を1増やす。`PIN_MAX_FAILS` に達したら、ロック解除日時を今＋`PIN_LOCK_MINUTES` にし、操作ログに「認証ロック」を残す。エラー `AUTH_FAILED` を返す。
  3. 一致したら、失敗回数を0に戻す。トークン（`Utilities.getUuid()`）を作り、`CacheService.getScriptCache().put('auth:' + token, JSON.stringify({employeeId, expiresAt}), 分×60)` で保存する。`{token, expiresAt}` を返す。
- **検証**（`verifyToken(ctx)`）
  - キャッシュにトークンがあり、`employeeId === ctx.operatorId`、かつ期限内のときだけ有効とする。
- **認証の解除**（`logout(ctx)`）
  - キャッシュから消す。
- 暗証番号が発行されていない社員が認証しようとしたときは、エラー `AUTH_FAILED` を返し、「暗証番号が未発行です。管理者に連絡してください」と表示する。

## 4. 入力と保存

### 4.1 入力チェック（【Validator】 の `validateRequest(payload, level)`。level は `FORMAT` か `FULL`）

| 項目 | キー | FULL（必須） | 形式チェック（両方のレベル） |
|------|------|:-----------:|------------------------------|
| 部門 | deptCode | ○ | 部署マスタに有効な行として存在する |
| 種別 | categoryCode | ○ | 種別マスタに有効な行として存在する |
| 承認者 | approverId | ○ | §4.3 の条件を満たす（値があるときだけ確認） |
| 発注先区分 | supplierType | ○ | `マスタ` / `手入力` / `指定なし` のどれか |
| 発注先 | supplierCode / supplierName | 区分による | マスタ: コード＋枝番が発注先マスタに存在する。手入力: 名称が1〜100文字。指定なし: コードと名称を空にする |
| 納入先区分・納入先 | delivery* | 同上 | 納入先マスタで同じ判定をする |
| 購入物品名 | itemName | ○ | 100文字以内 |
| 型番 | modelNo | ― | 100文字以内 |
| 数量 | quantity | ○ | 全角は半角に直す。`^\d+(\.\d{1,QUANTITY_DECIMALS})?$` に一致し、0より大きい。保存前に先頭の余分な0を除く（`007` → `7`）。小数部はそのまま残す |
| 単位・補足 | unitNote | ― | 20文字以内 |
| 理由 | reason | ○ | 500文字以内 |
| 納品日 | deliveryDate | ― | `yyyy/MM/dd` の実在する日付（`yyyy-MM-dd` で受け取ったら変換する） |

- 文字数はサロゲートペアを1文字として数える（`Array.from(str).length`）。
- 文字列はすべて前後の空白を除いてから判定する。
- エラーは `{code:'VALIDATION', fields:{キー: メッセージ}}` で返し、画面は項目の横にメッセージを出す。

### 4.2 保存処理の流れ（`saveRequest(ctx, payload, mode)`）
mode は `DRAFT`、`COMPLETE`、`REQUEST`、`EDIT` のどれか。

1. ロックを取る（§11）。
2. **新規のとき**（`payload.requestId` が空）
   - 届出IDを採番し（§8）、入力者を操作者にする。
   - バージョン1、CSV出力回数0、削除フラグ FALSE にする。
3. **既存のとき**
   - 行を読み、`payload.version` と行のバージョンが違えば、エラー `CONFLICT` を返す。
   - 削除済みなら、エラー `NOT_FOUND` を返す。
4. mode を action に変換する（DRAFT→SAVE_DRAFT、COMPLETE→COMPLETE、REQUEST→REQUEST、EDIT→EDIT）。
5. 権限（§3）と遷移（§2）を判定する。
6. 遷移表のチェックの列に従って、入力チェックをする。
7. 入力値を行に反映する（入力者・ステータス・システム項目は payload から受け取らない）。
8. 遷移があれば、ステータスと各日時を更新する（§5）。
9. 承認済を EDIT したときは、K-07 の処理をする（CSV出力済フラグを FALSE にし、資材が未確定なら候補を計算し直す）。
10. 更新日時・更新者を設定し、バージョンを1増やして書き込む。
11. 操作ログを書く（§12）。通知のフックを呼ぶ（§13）。
12. `{requestId, version, status}` を返す。

### 4.3 承認者の候補と妥当性（K-12、K-28）
- **候補**（`getApproverCandidates(deptCode, applicantId)`）
  - 承認者対応表で、部署コードが一致し、有効なもの。
  - 社員マスタで有効な社員に限る。入力者本人は除く。
  - 優先順の昇順で返す。
- **初期値**
  - 候補が1人ならその人を自動で設定する。
  - 2人以上なら、優先順が最も小さい人を初期値にする。
  - 部門を変えたら、承認者を選び直す。
- **候補が0人のとき**
  - 画面に K-12 のメッセージを出す。
  - 承認依頼はエラー `VALIDATION`（approverId）にする。
- **承認依頼のときのサーバー側の確認**
  - approverId が上の候補に含まれていなければ、エラー `VALIDATION` を返す。

## 5. 日時と提出日・納期

| 操作 | 更新する列 |
|------|-----------|
| 新規作成 | createdAt、createdBy |
| REQUEST | requestedAt、requestedBy。submittedDate が空のときだけ今日の日付を入れる（D-18） |
| CANCEL_REQUEST | requestCanceledAt、requestCanceledBy |
| APPROVE | approvedAt、approvedBy。資材が未確定なら資材候補を計算する（§6） |
| REJECT | rejectedAt、rejectedBy、rejectReason |
| CANCEL_APPROVAL | approvalCanceledAt、approvalCanceledBy。csvExported を FALSE にする（K-07）。submittedDate は変えない（K-32） |
| MARK_REFLECTED | reflectedAt、reflectedBy |
| REVERT_REFLECTED | revertedAt、revertedBy。reflectedAt と reflectedBy を空にする（K-08） |
| DELETE | deleted を TRUE にし、deletedAt、deletedBy を入れる |

**納期の出力値**（`calcDueDate(request)`）
- 納品日があれば、それを使う。
- 無ければ、提出日の月末日を使う。月末日は `new Date(y, m + 1, 0)` で求める（閏年の2月は29日）。
- 書式は `CSV_DATE_FORMAT` で整える。
- 提出日が空になるのは承認依頼の前だけで、承認済には必ず値がある。万一空なら、承認日の月末を使い、操作ログの詳細に警告を残す。

## 6. 資材コードの候補選定（【MaterialMatcher】。要 L259-277、K-10、K-11）

### 6.1 前処理
- 名称の正規化 `normalizeName(s)`: NFKC で正規化し、前後の空白を除き、スペースを全部除き、英字を小文字にする。
- 資材名の発注先部分 `supplierPartOf(name)`
  - 全角・半角の「：」で最初に区切った後ろの部分を取る（例: `消耗品（事務用品）：西本商店（生産管理部共通）` → `西本商店（生産管理部共通）`）。
  - 区切りが無ければ空にする。
- 発注先名の正規化
  - `normalizeName` の後で、`株式会社`、`(株)`、`有限会社`、`(有)` を除く。
- 対象の資材: `invalid` が `0` の行だけを使う。

### 6.2 発注先条件 `supplierMatch(material, request)`

| 発注先区分 | 判定 |
|-----------|------|
| マスタ | `material.makerCode === supplierCode` または `material.stockCode === supplierCode`。<br>または、`supplierPartOf(material.name)` に、発注先マスタの略称（略称が空なら名称）が含まれる（どちらも正規化して比べる）。<br>枝番は比べない |
| 手入力 | 正規化した `supplierPartOf(material.name)` と、正規化した入力名称の、どちらかがもう一方を含む（それぞれ2文字以上のとき） |
| 指定なし | 常に一致とする（発注先条件を外す） |

### 6.3 優先順と結果
1. **順位1**: `normalizeName(itemName)` が、`normalizeName(material.name)` または `normalizeName(material.nameInCompany)` と一致する。
2. **順位2**: 種別（`material.type === categoryCode`）、発注先（§6.2）、部門（`material.deptCode === deptCode`）がすべて一致する。
3. **順位3**: 種別と発注先が一致し、`material.deptCode` が部署マスタの共通部署コードと一致する。共通部署コードが空なら、この順位は飛ばす。
4. **順位4**: 種別と発注先が一致する（部門は問わない）。

**並べ方と保存**
- 同じ資材は、最も高い順位にだけ残す。
- 順位の昇順、次に資材コード・枝番・サブ枝番の昇順で並べ、上位 `MATERIAL_CANDIDATE_LIMIT` 件を残す。
- 資材候補JSONの形式:
  `[{"rank":2,"code":"000000000001591","branch":"","subBranch":"","name":"…","packQty":"1","deptCode":"23"}]`
- 資材が未確定（`materialFixed !== TRUE`）なら、先頭の候補を資材コード・枝番・サブ枝番・資材名・入数に「仮設定」する。候補が無ければ、これらを空にする。

**計算する時機**
- 承認したとき（T6）
- 承認済を修正したとき（資材が未確定の場合だけ。K-07）
- 経理・管理者が「候補を再計算」を押したとき（RECALC_MATERIAL）

**性能**
- 資材マスタは約4800行なので、1回の計算で `getValues()` を1回だけ呼び、メモリ上で判定する。

### 6.4 経理による確定と補完（K-39、K-40）
- **資材の確定**（`fixMaterial(ctx, requestId, version, material)`）
  - material が `{code, branch, subBranch}` のとき: 資材マスタで存在を確認し、資材名と入数を資材マスタからコピーする。
  - material が `null` のとき: 「資材なしで確定」として、資材の列を空にする。
  - どちらの場合も、`materialFixed=TRUE`、資材確定者、資材確定日時を設定する。
  - CSV出力済の届出で値が変わったら、csvExported を FALSE にする（再出力が必要になるため）。
- **資材の検索**（`searchMaterials(ctx, query)`）
  - キーワード（正規化して、名称・社内名称・コードとの部分一致）、種別、部門で絞り込む。
  - 最大50件を返す。無効な資材は除く。
- **コードの補完**（`fillCodes(ctx, requestId, version, {supplier, delivery})`）
  - 発注先・納入先のコードと枝番を設定する。値はそれぞれのマスタに存在するものに限る。表示・非表示は問わない。
  - 区分と名称は変えない。
  - コード補完者・補完日時を設定する。値が変わったら、csvExported を FALSE にする。

### 6.5 警告の判定（承認済一覧で使う）
| 警告 | 条件 |
|------|------|
| コード未設定 | 発注先コードまたは納入先コードが空 |
| 資材未確定 | `materialFixed !== TRUE` |
| 要再出力 | `csvExportCount > 0` かつ `csvExported === FALSE` |

## 7. CSV出力（【CsvExport】。要 L224-255、K-16、K-20、K-21）

### 7.1 対象と順序
- 対象は、指定した届出IDのうち、ステータスが承認済またはシステム反映済のもの（K-09）。それ以外が含まれていたら、エラー `INVALID_STATE` を返す。
- 各届出のバージョンを照合し、違えばエラー `CONFLICT` を返す。
- 行は届出IDの昇順で出力する。

### 7.2 列キー
| 列キー | 出力値 | 値がないとき |
|--------|--------|-------------|
| `SUPPLIER_CODE` | 発注先コード | 空 |
| `SUPPLIER_BRANCH` | 発注先枝番（K-21。初期設定では出さない） | 空 |
| `DELIVERY_CODE` | 納入先コード | 空 |
| `DELIVERY_BRANCH` | 納入先枝番（同上） | 空 |
| `MATERIAL_CODE` | 確定した資材コード（`materialFixed === TRUE` のときだけ。要 L231） | 空（未確定・資材なしで確定のとき） |
| `MATERIAL_BRANCH` | 確定した資材の枝番（同上） | 空 |
| `MATERIAL_SUB_BRANCH` | 確定した資材のサブ枝番（同上） | 空 |
| `PACK_QTY` | 確定した資材の入数。出力する資材コードが空なら空 | 空 |
| `QUANTITY` | 数量（保存した文字列のまま。K-34） | ― |
| `DUE_DATE` | 納期（§5 の `calcDueDate`） | ― |
| `REQUEST_ID` | 届出ID（予備） | ― |
| `ITEM_NAME` | 購入物品名（予備） | 空 |
| `MODEL_NO` | 型番（予備） | 空 |

- `CSV_COLUMNS` に無い列キーや、`CSV_HEADER_NAMES` との数の不一致があれば、出力前にエラー `SYSTEM`（設定エラー）を返す。
- 仮設定（未確定）の資材コードは出力しない（D-09、要 L231）。出力前の確認ダイアログで「資材未確定」の件数を知らせ、経理が確定し忘れないようにする。
  - 「仮設定の値も出力する」へ変える場合は、この行と 08 の TC-CSV-07 を直す。

### 7.3 ファイル形式（仮仕様。U-10）
| 項目 | 設定キー | 初期値 |
|------|---------|--------|
| 文字コード | `CSV_CHARSET` | Shift_JIS |
| 区切り | `CSV_DELIMITER` | `,` |
| 囲み | `CSV_QUOTE_MODE` | MINIMAL（区切り文字・`"`・CR・LFを含むときだけ `"` で囲み、`"` は `""` にする） |
| 改行 | `CSV_LINE_ENDING` | CRLF（最終行の後ろにも付ける） |
| 見出し行 | `CSV_HEADER` / `CSV_HEADER_NAMES` | あり |
| 日付 | `CSV_DATE_FORMAT` | yyyyMMdd |
| コード | ― | 文字列のまま（先頭の0を残す） |
| ファイル名 | `CSV_FILENAME_PATTERN` | `物品購入届_yyyyMMddHHmmss.csv` |

**生成手順**
1. 文字列を組み立てる。
2. `Utilities.newBlob('', 'text/csv', fileName).setDataFromString(csv, charset)` で Blob を作る。
3. `Utilities.base64Encode(blob.getBytes())` を返す。
4. 予備の列（購入物品名など）に Shift_JIS で表せない文字があると `?` になる。初期の列はコードと数字だけなので影響しない。

### 7.4 出力後の記録
- 出力した届出ごとに、次を更新する。
  - csvExported を TRUE
  - csvExportedAt、csvExportedBy
  - csvExportCount に1を足す
  - バージョンに1を足す
- 操作ログに「CSV出力」を1件ずつ残す。詳細JSONにはファイル名を入れる。
- ステータスは変えない（要 L255）。
- 戻り値: `{fileName, mimeType:'text/csv', base64, count, results:[{requestId, version}]}`
  - 画面は、返ってきたバージョンで一覧の値を更新する。

## 8. 届出IDの採番（K-15）
- 形式: `{REQUEST_ID_PREFIX}-{yyyyMMdd}-{連番}`
  - 連番は3桁でゼロ埋めし、1000件目以降は桁を増やす。
  - 日付は作成日（Asia/Tokyo）。
- ロックの中で、届出データの届出ID列から同じ日付の接頭辞を持つものを探し、連番の最大値に1を足す（削除済みも数える）。

## 9. 添付書類（【Attachment】。要 L104-109、K-17、K-29）
- 添付の枠は2つ（slot 1: 見積書など金額がわかるもの、slot 2: 納品書）。
- **アップロード**（`uploadAttachment(ctx, requestId, version, slot, file)`）
  1. 権限（修正できる人か）とバージョンを確認する。
  2. 拡張子が `ATTACHMENT_ALLOWED_EXT` に入っているか、サイズ（Base64 から求めたバイト数）が `ATTACHMENT_MAX_MB` 以下かを確認する。
  3. 届出IDのサブフォルダを探し、無ければ作る。
  4. ファイルを作る（ファイル名は `slot{n}_{元のファイル名}`）。
  5. 同じ枠に既存のファイルがあれば、`setTrashed(true)` でゴミ箱へ移す（D-20）。
  6. 行の添付ID・ファイル名を更新し、バージョンを1増やす。操作ログに「添付追加」または「添付差替」を残す。
- **削除**（`deleteAttachment`）: ゴミ箱へ移し、列を空にする。操作ログに「添付削除」を残す。
- **取得**（`getAttachment(ctx, requestId, slot)`）: `{fileName, mimeType, base64}` を返す。全員が取得できる（K-41）。
- 新規の届出は、先に保存して届出IDを得てから、1ファイルずつアップロードする。画面がこの順番を管理する。
- 届出を論理削除しても、添付は残す（K-29）。
- クライアントでも、送る前にサイズと拡張子を確認する（大きいファイルを無駄に送らないため）。

## 10. マスタ取込（【MasterImport】）
- 03 §4 の規則で実装する。入口は `importMasters(target)`（`'MATERIALS'`、`'SUPPLIERS'`、`'EMPLOYEES'`、`'ALL'`）。
- `ALL` は次の順で実行する: 資材 → 部署・種別の生成 → 発注先 → 社員。
- `IMPORT_FOLDER_ID` のフォルダから、決まったファイル名（大文字・小文字は区別しない）を探す。同じ名前が複数あれば、更新日時が最新のものを使う。
- 結果として `{target, fileName, rows, inserted, updated, disabled}` を返し、操作ログに残す。
- 実行時間の上限（6分）に備えて、資材の書き込みは `clearContents` と `setValues` を1回ずつにする。
- 取込の後で `CacheService` のマスタのキーを消す。

## 11. 排他制御と楽観ロック（D-21）
- 更新を伴う API はすべて、【Repository】の `withLock(fn)` で包む。
  - 中では `LockService.getScriptLock().tryLock(10000)` を使う。
  - ロックが取れなければ、エラー `BUSY`（「混み合っています。少し待ってからもう一度お試しください」）を返す。
- ロックの中で行を読み直し、`version` を比べる。違えばエラー `CONFLICT`（「他の人が先に更新しました。画面を再読み込みしてください」）を返す。
- 一括操作（CSV出力・反映済にする）は、全件のバージョンを先に確認する。1件でも違えば、どれも更新しない。
- 行の位置は、届出IDで探して求める（`findRowIndex(requestId)`）。行を削除しないので、位置は変わらない。

## 13. 通知（【Notifier】。D-11、要 L303-312）
- `notify(event, request)` を、REQUEST・REJECT・APPROVE の後で必ず呼ぶ。
- `NOTIFY_ENABLED` が FALSE なら、何もせずに戻る（初版）。
- TRUE のときの送り先
  - REQUEST: 承認者
  - REJECT: 入力者
  - APPROVE: 入力者と経理担当全員
  - アドレスは社員マスタのメールを使う。
- 送信は `MailApp.sendEmail` で行う。初版では、送信処理の中身を「ログに出すだけ」のスタブにしてよい。
  - 有効にするときは、スコープ `script.send_mail` を追加し、権限を承認し直す必要がある（02 §3）。
